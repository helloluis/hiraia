# QVAC in Tala: evidence and integration proposal

Research only — 14 November 2026. **No integration is authorised by this document. Luis approves the plan first.** No dependencies, application code, build configuration, models or APKs were changed for this task.

Reviewed integration commit `4cea0ffcf` after `git merge tala-v1`; read student/server/Kotlin sources using `git show` / `git grep` against `tala-0.4.x` commit `7d85aa521e392bb35c3297bf58ce77100a6a9259`. Website and official package/documentation observations are dated, not permanent compatibility guarantees. Version numbers below must be rechecked when implementation is approved.

## Recommendation and decision

QVAC can run inside Expo prebuild: ejecting is **not** necessary. It runs a separate Bare/native inference worker while Hermes continues to render React Native. However, the supported Android runtime does **not** cover Tala's binding Android 8 / 2 GB reference device. Installing the dependency and hiding an AI button would not solve native minimum-SDK or ABI restrictions.

Keep today's small, offline-first planning APK intact. If Luis approves, first build a **separate experimental ARM64 QVAC variant**, without bundled weights, targeting supported modern phones. Prove one useful capability: bounded roster-name suggestions, with the existing rules/parser/review flow always available. Use a small downloadable model, explicit opt-in, and synthetic evaluation names. Section regeneration can follow quality/performance evidence; full multi-grade lesson generation should remain on the cloud path for now.

Do not represent an unused SDK dependency as an offline AI feature or as completion of the student-data privacy gate. If inclusion in the single standard APK is mandatory, Luis must first resolve the reference-phone/platform and payload-budget conflicts, or fund a substantially larger unsupported-runtime backport investigation.

## Evidence: current official QVAC distribution

QVAC is Tether's local-inference toolkit, not a bundled model or a hosted lesson-writing API. Its public product page describes local AI across mobile/desktop and Apache-2.0 distribution. Model quality and device capacity remain separate concerns. [Official SDK product](https://qvac.tether.io/products/sdk).

Observed npm registry metadata: `@qvac/sdk` latest **0.23.0**, license **Apache-2.0**; the official `sdk-v0.23.0` GitHub release was published **2026-11-02**. `react-native-bare-kit` latest observed **0.17.1**, whereas the current SDK setup documents **^0.16.0**. The correct tested pair must be pinned, not selected by independent “latest” upgrades. The SDK's own unpacked package is only **1,604,283 bytes**; that excludes the native dependency closure and weights. [Versioned official package source](https://raw.githubusercontent.com/tetherto/qvac/sdk-v0.23.0/packages/sdk/package.json), [npm SDK page](https://www.npmjs.com/package/@qvac/sdk), [official release](https://github.com/tetherto/qvac/releases/tag/sdk-v0.23.0).

| Route                         | What is actually distributed                                                                                                                        | Constraints verified from official documentation                                                                                                                                                                                                                                                                                                                   |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| JS/TS, recommended Expo route | npm SDK/client, a bundled Bare worker over RPC, native addon packages, `react-native-bare-kit`, SDK Expo config plugin                              | Expo >=54; current setup names Bare kit ^0.16.0 and mobile bundling Node ^22.21.0 or >=24.9.0. Our Node 24.21.0 meets this. Prebuild relinks addons after installs. Native development/release build required; Expo Go is not an inference host. [JS/TS setup](https://docs.qvac.tether.io/sdk/js-ts-sdk/).                                                        |
| Native Kotlin alternative     | Capability-specific Android AARs plus Kotlin client, distributed as GitHub-release Maven repository archives; not a public Maven Central dependency | LLM profile provides completion/embeddings; API29+, ARM64; Kotlin >=2.3, with documented newer compiler dependency. Its private `:qvac_worker` service is a separate native integration. Tala demo's Kotlin 2.1.20 would need investigation/upgrading. No existing Expo bridge supplied by this choice. [Kotlin SDK](https://docs.qvac.tether.io/sdk/kotlin-sdk/). |

**Packaging floor is not the support floor.** The JS Expo recipe sets minSdk **29** (Android 10), but the current worker support matrix lists Android **12+ / ARM64**, with Vulkan/OpenCL capabilities. AAR install requirements also say API29. Treat Android12+/ARM64 as the supported initial target until QVAC resolves the API29–30 discrepancy. Neither statement covers Android8/API26 or 32-bit ARM. Linux/macOS/Windows/iOS are also documented, with their own architecture/OS/backend requirements; desktop availability does not imply Android x86 support. [System requirements](https://docs.qvac.tether.io/sdk/system-requirements/).

Text generation uses llama.cpp-compatible **GGUF**; SDK calls load, completion and unload run inference in the worker/native engine. Model-specific support must match the exact bundled engine, rather than assuming every newly published GGUF architecture works with the student's older engine. [Text-generation API](https://docs.qvac.tether.io/sdk/ai-capabilities/text-generation/).

The current Expo tutorial explicitly selects only completion in `qvac.config.json`; otherwise all capabilities may be included. New native packages include `@qvac/fabric-android-arm64` and an iOS counterpart; the tutorial says both can be needed to bundle the cross-platform worker even for Android-only prebuild. Prefer explicit audited pins over `installMissingPrebuilds: true`, which mutates package.json during prebuild. Its embedded SDK version example is stale relative to its page heading: use versioned metadata/plugin output to establish exact pins. [Official Expo tutorial](https://docs.qvac.tether.io/resources/tutorials/expo/).

Official docs currently require physical-device inference tests and warn that llama.cpp does not run on emulators. Our previous ARM-translated emulator smoke test proves Tala's ordinary RN/SQLCipher app works, **not QVAC inference**. Do not use it as the QVAC acceptance device.

### The roster privacy gate needs a precise decision

Current PRD **§12.4.1** says production student-data processing uses a **locally hosted model run by Hiraia**, gateway route `local` (or `rules`), cloud prohibited in production, and the local model must meet the roster adversarial evaluation baseline. That describes Hiraia-controlled hosting, not necessarily a phone. Existing mobile rules-only parsing already works offline; adding QVAC is not necessary to preserve that fallback.

A vetted on-device path could meet the intent more strongly for those supported phones, but changing the specified processing location/routing and defining acceptance needs Luis/orchestrator approval. It closes no gate merely by existing in the APK. Until the model passes, production stays rules-only for names; on unsupported phones it remains rules-only. If “local” must work for every supported teacher phone with model assistance, a Hiraia-hosted local model remains the practical architecture. Lesson drafting can still use today's cloud route independently.

## Payload, memory, battery and licensing consequences

The delivered Tala demo baseline is **22,785,838 bytes**, both ARM ABIs, before QVAC. PRD §14.1 now caps APK download at **40 MB**, installed app **90 MB**, normal RAM **250 MB**, peak **350 MB**, Hermes **6 MB**. Model weights cannot fit the current APK/local-data/weekly-data budgets. This is a product/budget decision, not a Metro tuning problem.

| Packaging choice                         | Planning effect; not a measured Tala QVAC build                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SDK + completion worker, no weights      | Budget **+40–120 MB APK** as a conservative investigation envelope, not a release commitment; native selection/compression can materially change it. Result roughly **63–143 MB total** against the current universal baseline (an ARM64-only baseline is smaller). Likely violates the 40 MB gate; measure before choosing a product tier. Worker/native files count even when omitted from the Hermes size report. |
| Same with tiny bundled Q4 model          | Add approximately **80–300 MB** more. Quantised weights generally compress poorly; copying from packaged asset to a usable model path can add another installed copy. Not recommended.                                                                                                                                                                                                                               |
| Same with Qwen0.6B Q4 / Hiraia2B bundled | Add approximately **350–450 MB / 1.274 GB** respectively. Clearly unsuitable for baseline distribution.                                                                                                                                                                                                                                                                                                              |
| Opt-in model download                    | Keeps weight bytes out of the APK, not native runtime bytes. Requires a separate disclosed storage/data allowance, resumable transfer, verification, cancellation, and model removal controls; does not fit the normal weekly sync allowance or make a never-downloaded phone work offline.                                                                                                                          |

Size evidence, **not equivalent to APK delta**: official npm metadata for `@qvac/fabric-android-arm64@0.29.2` reports **106,182,041 unpacked bytes** across 16 files. The official 0.23.0 Kotlin LLM Maven repository archive is **125,721,461 bytes**; the all-capabilities archive is **203,439,749 bytes**. These contain different packaging/dependency sets, can include duplication and are not the final compressed app. The 1.6 MB SDK tarball size alone is misleading. [Official native package metadata](https://registry.npmjs.org/@qvac%2Ffabric-android-arm64/0.29.2), [official release assets](https://github.com/tetherto/qvac/releases/tag/sdk-v0.23.0).

A small-name model might add hundreds of MB resident while running; a 2B model adds well over the baseline's peak budget. Memory-mapping can defer paging, not manufacture RAM. Use real available-memory/low-RAM checks before loading, unload after use/pressure, and never sacrifice unsent lessons to retain a model. New SDK `assessModelFit` is advisory and not a speed or safety guarantee; older SDK 0.17.1 should not be assumed to expose it. [Model-fit documentation](https://docs.qvac.tether.io/sdk/models/assess-model-fit/).

Inference occupies CPU/GPU, drains battery and can thermally throttle or trigger Android's low-memory killer. No honest tokens/sec, runtime RAM or temperature promise can be made without a phone. Start with one foreground task, bounded context (e.g. 1024–2048 for name snippets/short sections), bounded output and validated options. Probe supported GPU paths and a baseline CPU fallback; do not infer GPU capability from RAM. Stop/cancel/unload on backgrounding/pressure initially, keep the original text saved, and resume a durable request later rather than promising a persistent KV session. No foreground service or persistent wake lock is proposed for the JS route. Background inference would be a separate notification/OS/battery design, not automatically supplied by adding the SDK. [Worker lifecycle](https://docs.qvac.tether.io/sdk/runtime/lifecycle/).

**Licence work before shipping:** retain Apache-2.0 licence/copyright and applicable NOTICE files; mark modifications; inventory licences of the actual linked native/transitive packages (including their bundled components). Apache does not require exposing the whole app source or using a badge; it does not grant general trademark/endorsement rights. Audit each selected model's separate licence, base/derivative terms and redistribution requirements; the SDK's licence does not license arbitrary model weights or training data. Include third-party notices in the APK/About and distribution documentation. This is a concrete release checklist, not a completed legal review. [QVAC's actual Apache licence](https://raw.githubusercontent.com/tetherto/qvac/main/LICENSE).

## Proposed implementation, after Luis approves

These are ordered future steps, not commands executed or edits made now. Scope future code to Tala V1-owned paths; the orchestrator owns any root/contract changes.

1. **Choose the supported product tier and a physical phone (0.5–1 engineering day).** Preserve the existing Android8 baseline. Approve a separate experimental application ID/build variant under `packages/tala-mobile` (proposed QA ID `com.hiraia.tala.next.qvac`, not a decision already made). Start on Android12+/ARM64, preferably 6 GB+. Choose whether success means a verified worker or useful evaluated roster suggestions. Obtain a device with an older baseline ARMv8 CPU as well as a modern one for CPU/backend tests.
2. **Freeze a dependency/toolchain matrix in an isolated spike (1–2 days).** Preferred target is current SDK **0.23.0**, not an unbounded caret; pin its compatible Bare kit, worker bundler and exact native packages after inspecting their versioned manifests. Add expo-build-properties; Tala already has SDK54/RN0.81.5, expo-device/file-system and suitable Node. Student **0.17.1 / Bare kit0.12.3 / RAG0.6.4 / llama0.39.4** is a reproducibility reference or explicitly time-boxed legacy comparison, not a silent downgrade/new long-term support commitment.
3. **Protect the flattened monorepo before installing.** Root hoisting already exists; never toggle it or upgrade the student/sidecar packages as a shortcut. A 0.23/0.17 collision can misbundle worker APIs versus native engines. Prefer an isolated dependency tree for the experimental build and explicitly resolved SDK-local addon paths. If remaining in the shared tree, require exact package-local pins, capture actual resolution from the worker and linker, and fail on mismatched versioned `.so` names. Request orchestrator review before a root-level dependency/lock adjustment. The student RAG pin is a historical safeguard, not a reason to add obsolete RAG to a completion-only new SDK blindly.
4. **Configure Expo, then a no-model native smoke build.** Add SDK's config plugin and completion-only `qvac.config.json` to the QVAC variant; set its native minimum SDK/ARM64 ABI explicitly. Use minSdk31 initially unless vendor evidence supports a lower runtime tier. Keep Hermes and current app ID/signing independent from 0.4.x. Re-run prebuild after installs, and verify the generated worker bundle/addon manifest and actual APK native contents. Try upstream plugin first: newer docs claim it links addons; only copy/adapt the student's bare-link fallback if the pnpm failure is reproduced. Preserve plugin ordering, generated-directory ownership, version checks, baseline CPU compatibility and notices. Do not copy ChromeOS overlays, model/voice assets, OTA settings or cleartext mirror exceptions.
5. **Preserve baseline builds at the native level.** A JS feature flag is insufficient: native dependency manifests can raise the whole APK's minSdk before any JS runs. Baseline must omit QVAC/Bare native autolinking, SDK prebuild mods and worker assets, and still package both existing ARM ABIs. Prove baseline APK diff/minSdk/startup/no-QVAC-library checks. If deterministic exclusion cannot be proven, use a genuinely separate experimental project/dependency tree rather than jeopardising the released baseline. No `tools:overrideLibrary` workaround or purported ARMv7 vendor backend.
6. **Keep Metro and Bare responsibilities separate.** Reuse Tala's current monorepo source resolver (`metro.config.cjs`); add only required resolution/asset exclusions. Borrow student's singleton/hierarchical-resolution safeguards as needed. Let QVAC's plugin/bare-pack create its own worker: do not put Bare filesystem/network/native modules on Hermes or add GGUF to general Metro asset extensions. Count separately Hermes HBC, Bare worker, native ELF libraries and weights in budget reports. Native changes require a fresh development/release APK; Expo Go or a JS-only OTA cannot deliver the runtime.
7. **Add explicit model delivery and lifecycle (1–2 days).** Use opt-in Wi-Fi download; no model fetch or worker creation in sign-in/setup/This Week startup. A manifest identifies model/version/licence, byte length, cryptographic digest and engine compatibility. Resume into a temporary file, verify before atomic install and use a local filesystem modelSrc. Reuse the student's transfer/captive-portal lessons, while verifying a supported streaming hash solution rather than copying multi-GB JS reads or relying on MD5 for authenticity. Retain the existing encrypted store and key-prepared transaction fix. User data/model paths must not leak via URL/query/logs. Give cancellation, progress, low-storage checks, delete/re-download and rollback to last valid model; no P2P discovery needed for the first spike.
8. **Wire only a bounded, reviewable feature (2–3 days).** Proposed future `src/features/local-ai/` adapter owns worker/model lifecycle and local-only durable jobs. Roster rules extract/withhold sensitive cells first; send only unresolved name snippets to the local model. Validate returned rows, preserve exact original spellings, flag uncertainty and require existing review actions. No external tool/MCP/cloud calls, telemetry payloads or prompt/output logging. Explicitly audit the SDK's registry/P2P/logging defaults and test inference with network blocked after download. Never automatically fall back to cloud for names. Any required client-local routing/provenance contract addition goes to orchestrator approval.
9. **Connect section generation only after the first gate (additional 2–4 days).** Feed cached official objectives and explicit group context; retain structured section validation, AI marker/check notice, revisions and one durable batch on Apply. Stream display separately from persisted teacher content; preserve current draft through cancel/crash. Local jobs must not call `generation.create` merely to get a queue ID or consume a cloud allowance. Record model/version/origin through an approved provenance shape. Existing server-queued generation and prefilled-template fallback remain available. Do not claim full offline multi-grade drafting from a single short completion demo.
10. **Measure and decide whether to ship (2–3 days, partly overlapping feature work).** On real supported phones: loader/backend success, cancellation, airplane-mode inference, no network/student-data leakage, repeated load/unload, Android process kill/reopen, RAM/PSS peaks, installed/APK sizes, startup/editor responsiveness, hot/battery/low-memory behavior. Run all Tala tests, type-check, export/Hermes budget and one-at-a-time Gradle builds with <=2 workers; stop own daemons. Compare model roster accuracy against the adversarial cloud/rules evaluation, including Filipino names, accents, particles, suffixes, ambiguous columns and exact-as-written fallback. Obtain Luis approval before changing a PRD gate, distribution requirement or public branding claim.

Effort estimate (engineering time, not a calendar ETA): **1–2 days** for a no-model native spike after the support decision; approximately **6–10 working days** for an opt-in, evaluated roster-assistance candidate with device testing, plus model/domain evaluation iterations. Optional section drafting adds **2–4 days**. A Kotlin-AAR bridge adds roughly **3–5 days** of compiler/service/bridge investigation beyond the JS route. An Android8/ARMv7 source backport is **weeks of uncertain work**, with no justified delivery estimate or guarantee; request vendor support first. Device availability, model quality and hoisting isolation can change these estimates.
