# tala-activity

Classroom-activity collection for Tala V1.0, ported from Hiraia Tala 0.4.4 (Kotlin, branch
`tala-0.4.x`) into the Expo app as a local native module plus a TypeScript feature (PRD §6.7).

- **Contract:** `PROTOCOL.md` — the wire protocol as implemented by Tala 0.4.4 and student app 0.4.24.
- **Wiring for Worker E:** `INTEGRATION.md`. **ACT-2 migration design:** `UPGRADE.md`.
- **Native (Android 10+):** `android/src/main/java/expo/modules/talaactivity/`
  - `TalaActivityModule.kt` — Expo module `TalaActivity`: availability/permissions/radios, keystore
    class keys, protocol crypto, Nearby advertising, card catalog.
  - `TalaCrypto.kt`, `ClassHint.kt`, `ManualEnrollment.kt`, `CardCatalog.kt` — pure JVM, unit-tested.
  - `ClassKeys.kt` — AndroidKeyStore RSA-2048 per class, alias `hiraia.tala.class.<id>` (= 0.4.x).
  - `NearbyAdvertiser.java` — Nearby Connections wrapper (Java, like the student module).
- **TypeScript:** `../../src/features/activity/`
  - `protocol.ts` constants/validators; `session.ts` collector state machine; `store.ts` SQLite store;
    `identity.ts`; `learning.ts` totals/days/avatars; `catalog.ts`; `qr.ts` QR+PNG; `upgrade.ts` import;
    `runtime.ts` glue; `ActivityScreen.tsx`, `LearnerScreen.tsx`; `strings.ts` (fil/en).
- **Vectors:** `vectors/protocol-vectors.json`, generated by `vectors.test.ts`, consumed by the Kotlin
  tests (`android/src/test/...`), so the JVM OAEP/GCM/HMAC and the TypeScript side agree byte for byte.

## Commands

```bash
# from packages/tala-mobile
node_modules/.bin/tsc --noEmit
node_modules/.bin/tsx --test "src/features/activity/*.test.ts"      # see INTEGRATION.md §1 about pnpm test
node modules/tala-activity/scripts/sync-card-catalog.mjs             # copy the 0.4.x catalog (needs tala-0.4.x)
# Kotlin unit tests (standalone JVM build; the Android library is built by the app):
source ~/.config/hiraia/build-env.sh && gradle -p modules/tala-activity/android/jvm test --max-workers 2
```

## Design notes

- Protocol state lives in TypeScript (`session.ts`) so the whole exchange is unit-tested; the native side
  does only what needs the platform (radios, keystore, javax.crypto, the 1.9 MB catalog).
- Activity data never leaves the phone: no relay/upload tables were ported (ACT-5/PRIV-10). The store is
  its own SQLCipher file; deleting a class deletes its rows and its key.
- The QR is drawn by a dependency-free encoder (`qr.ts`, port of Nayuki's qrcodegen, MIT) to a PNG data
  URI. Verified offline with zxing-cpp 2.x: a 544-byte Tala payload (and Filipino text) decodes byte for
  byte at EC levels L, M, Q and H. Level M is used (smaller symbol than 0.4.x's H; no centre badge).
- The card catalog is read from the `tala-0.4.x` branch at build time (`scripts/sync-card-catalog.mjs`),
  never edited here, so ids stay append-only by construction; it is parsed natively and lazily.

## What could not be verified here, and the manual test for Luis

No Android build ran (Worker E owns it) and this host has no radios, so real Nearby discovery and transfer
are untested. The exact two-phone test, once E has a `com.hiraia.tala.next` build:

1. Phone A (teacher): install the V1 build, create a class, open Class → **Collect activity**. Expect the
   permission prompt (Nearby devices / Bluetooth), then "Nearby ready · Waiting for student phones".
2. Phone B (student, Hiraia 0.4.24 or later): Settings → JOIN A CLASS → scan the QR shown on A. Expect B
   to show the class name from A's QR, and A's learner list to show B's profile(s) as **Connected**, then
   **Received**, with card counts after a few cards are viewed on B.
3. Backup code: on A tap **Refresh code**; on B type the 12-character code instead of scanning (a second
   profile or after leaving the class). Expect the same class name on B and a new tile on A.
4. Leave: on B leave the class for one profile. Expect that tile to disappear from A's list (it stays in
   the learner's page only if you open it before it refreshes) and to return when B re-joins.
5. Remove: on A open a learner → **Remove from class** → confirm. Expect the tile gone; have B view more
   cards and sync — A must not show them again.
6. Compatibility: repeat step 2 with a phone still on **Tala 0.4.4** as the teacher and the same B, to
   confirm B's binding to the V1 class does not disturb the 0.4.4 class and vice versa (different class ids).
7. Background: press Home on A while B is syncing; expect B to retry; return to A → collection resumes.
8. Low-end check: open a learner page on a 2 GB phone; the first open parses the catalog natively — note
   the delay (target < 1 s) and memory (`adb shell dumpsys meminfo com.hiraia.tala.next`).
