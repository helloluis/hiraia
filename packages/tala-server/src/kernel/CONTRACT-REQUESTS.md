## 2. Decision still open: sign-up reveals that an email is registered

`auth.register` returns a session, so signing up with an address that already has an account must fail
visibly (`409 conflict`, `details.reason = 'email_taken'`). Sign-in, reset and verification reveal nothing.
Sign-up is rate limited per address. To hide it at sign-up as well, `auth.register` would have to answer
`Ok` for every address and create the session only after the emailed link is opened. That changes the
sign-up flow on web and mobile, so it is Luis's call.

## 2a. Open items for Luis from Google sign-in

- **A Google-only account can be deleted with the session and the word `DELETE` alone.** `account.delete` has
  no field for a fresh Google proof, so a borrowed, still signed-in device is enough. Closing it needs an
  optional `idToken` on `account.delete`.
- **Lapsed email ownership.** Someone holding a Google account whose confirmed email they no longer control can
  create a Tala account under that address. If the real mailbox owner later uses "Forgot password", they get
  in, but the Google link stays attached. Closing it means removing Google links on a password reset, which
  would also hit the ordinary case of a teacher who simply forgot their password.
- **Joining accounts asks for both passwords** (decided: keep). Without the signed-in account's own password, a
  borrowed signed-in device could merge another account in and inherit its Google link as a permanent way in.

## 2b. Requested: post-class writing on a locked plan

- **`'post_class'` in `PlanRevisionMeta.reason`** (`contracts/api.ts`). The server stores writing in a
  post-class part of a locked plan as its own kind of revision, `post_class` (§3 row o). The contract's list
  has no such value and every response is checked against it, so `plans.revisions` and `plans.revision` show
  it as `save` with `locked: true` for now. That pair also covers a change of dates, the "submitted" note,
  the unit or archiving on a locked plan, so a client cannot yet tell the two apart. Nothing else is needed:
  the server reads the contract's list at start-up and shows `post_class` as itself once it is there
  (`shownReason` in `modules/core/revisions.ts`; checked by `postclass.test.ts` either way). No client reads
  these two routes today.

| d   | Only `applied` results are remembered for replay, for 30 days. A replayed conflict, locked or invalid mutation is judged again. | n   | Which parts of a locked plan stay enterable is decided from the server's own records, never from anything in the mutation. When a lock is taken the server writes down, with the lock's revision, which keys the plan's template (built-in, or the owner's own) called post-class (`outsideLock`) and which keys were inside the lock (every other key of the template, and the key of every part the plan held that was not post-class). From then on: a key that was inside the lock is frozen, whatever happens to the template; a key that was post-class stays enterable, also when the template is later changed or deleted; a key that did not exist at lock time is enterable only if the template calls it post-class now (this is how `results` works on a plan locked before that part existed). Frozen means `locked` for an edit, a new record, a delete, a change of `key`, and moving a part in from another plan. A custom template with a built-in id is ignored. A plan locked before its template reached the server has every part it held frozen. A lock taken before this record was kept goes by the template as it is now. | Offer a part for writing on a locked plan only when the template marks it `outsideLock`. Creating the record for a post-class part on a locked plan is `applied`. Unlocking and locking again takes the template as it is then. |
| o   | Writing in a post-class part of a locked plan (also an archived one that keeps its lock) never touches the plan record: same `rev`, same `lock` with its `revision` and `revisionCode`, `aiDraft` stays false. The lock revision's snapshot is never altered. The writing gets a server revision of its own, stored as `post_class`: writing within 10 minutes shares one, the newest 20 are kept, and it is never merged with an ordinary save. When one push also changes the plan's dates, "submitted" note or unit, the one snapshot is `post_class`. A post-class part that arrives with `origin: 'ai'` and a new `gen.at` is `regenerate`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `plans.revisions` shows `post_class` as `save` with `locked: true` until the contract lists it (§2b).                                                                                                                           |
| p   | The lock check never requires a post-class part: not its record, not its content, also when a custom template marks it `required`. A required pre-class part is still required.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | The shared `validatePlanForLock` agrees (it skips `outsideLock` sections), so an app and the server refuse the same locks.                                                                                                      |
| q   | Joining accounts (`account.merge`) cannot change a locked plan. A part of the account being removed that names a plan locked in the surviving account, under a key that lock froze, is not brought over (a sync of it would have been `locked`); a post-class part is. A locked plan of the account being removed arrives locked, with the record of what its lock froze, unless it cannot arrive as it was locked: the surviving account already holds a part for that plan id under a frozen key, or already holds a record with the id of one of its frozen parts. Then it arrives open: a draft (an archived plan stays archived) with `lock` and `submitted` cleared and an `unlock` revision of its own; the lock revision stays in its history. Neither happens unless the two accounts used the same ids.                                                                                                                                                                                                                                                                                                                                  | After a merge, read plans back from the pull: a plan that was locked may have arrived as a draft.                                                                                                                               |

## 4. Smaller open items

- **Lenient push:** parse each mutation on its own so an unknown `entity` from a newer app is `invalid` for
  that one mutation, not a 400 for the batch (row i).
- **`TalaServerConfig`:** the trusted-proxy count is env-only (`TALA_TRUSTED_PROXY_HOPS`); a
  `network: { trustedProxyHops }` field would make it visible. A `mail` block is needed once a provider is chosen.
- **`ApiError.message` language:** plain English. Clients localise by `code` and these `details.reason`
  strings from the kernel and core: `no_credentials`, `unknown`, `expired`, `revoked`, `account_deleted`,
  `cross_site`, `body_too_large`, `not_utf8`, `invalid_json`, `content_type_must_be_json`, `bad_path`,
  `rate_limited` (with `retryAfterSeconds` when known), `email_taken`, `invalid_credentials`,
  `display_name_empty`, `password_too_short`, `password_too_common`, `password_too_simple`,
  `password_matches_account`, `link_invalid_or_expired`, `wrong_password`, `no_password`, `mail_unavailable`,
  `google_sign_in_not_available`. Validation failures carry `details.issues: [{ path, message }]`.
- **`RecordStore.get`** returns live records only (null for a deleted one); `list(…, { includeDeleted })`
  shows tombstones. **`checkTallies`** counts only accounts with a confirmed email, so one person cannot make
  a competency look widely checked by signing up many times.
