## QVAC and ChromeOS limits

Checked against the installed packages and current primary documentation on 29 September:

- SDK `@qvac/sdk` 0.17.1 links `@qvac/llm-llamacpp` 0.39.4 and
  `@qvac/embed-llamacpp` 0.30.1. Both ship **android-arm64 only** prebuilds.
  The private ChromeOS variant adds genuine Android x86_64 builds of both engines from
  the released QVAC source; the other worker addons already provide x86_64 prebuilds.
  ARM libraries are never copied into x86 directories. That upstream convenience script
  does not produce executable x86 code.
- [QVAC system requirements](https://docs.qvac.tether.io/system-requirements/) list Android
  12+, ARM64, physical hardware; Android emulator inference is explicitly unsupported.
  Successful experimental inference would not change vendor support status.
- [Google's ChromeOS device guidance](https://developer.android.com/develop/devices/chromeos/learn/device-support)
  warns that not every Intel Chromebook translates ARM64, and translation has performance
  costs. ARM64-only is insufficient to claim support for a mixed school fleet.
- [Google's VM guide](https://www.chromium.org/chromium-os/developer-library/guides/containers/cros-vm/)
  describes Linux/x86 VM tooling and the ARC-enabled `betty` board for Googlers. The public
  ChromiumOS VM workflow is not equivalent to a Chromebook Android-runtime test on this
  Apple Silicon Mac. A desktop-shaped Android AVD is **not a ChromeOS emulator**.

Final Chromebook acceptance needs real ARC validation on an ARM Chromebook and an
Intel/AMD Chromebook, including offline QVAC inference, read-aloud, free window resizing,
sleep/resume, mouse/keyboard-only operation and the actual school installation policy.
The x86_64 port does not establish vendor support or prove runtime compatibility on ARC.

## Native x86_64 build

`packages/mobile/scripts/build-qvac-android-x64.mjs` compiles the released engines in an
isolated, ignored source checkout. Pins live in `native/qvac-android-x64.json`: QVAC commit
`cba9434b05b708449393986ed8e58360dc58f61e`, Fabric 9840.1.1, NDK 29.0.14206865,
vcpkg 2025.12.12 and exact CMake/Bare build-tool versions. Neither the app's JavaScript
worker nor its installed packages are replaced.

Bare headers must be pinned to 1.30.0, contemporary with that QVAC release. Taking today's
default headers breaks `js_set_array_elements` at compile time after a C++ const-signature
change. The pin affects the isolated build dependency, not QVAC's inference code.

The port retains the baseline x64 CPU backend, CPU-specific variants with upstream runtime
feature checks, Vulkan and optional OpenCL. The first native Intel run exposed an upstream
Android loader defect: its basename fallback enumerated ARM backends only, causing both
models to fail with `make_cpu_buft_list: no CPU backend found`. The pinned
`native/qvac-x64-overlay` adds the 14 x86 backend names and rejects a zero feature score
before adding preference offsets. Its four native loader tests include baseline-only,
incompatible variants, an Ivy Bridge feature set and no compatible backend; a seeded
unsupported-CPU defect must fail. This patch is confined to the x86 source port.
The overlay inputs and actual binary hashes are recorded in its manifest. Prebuild
checks source/package-version agreement, every cached hash and actual ELF architecture;
the finished APK audit checks both ABIs, addon parity, shared-library dependencies and
QVAC's required Bare/C++ symbols against the libraries actually packaged. Negative tests
include ARM binaries deliberately placed in x86_64 directories and missing worker addons.
Compiled bytes and build pins enter the private OTA fingerprint. Licenses/notices and
build provenance are included in the APK.

The SDK's bundler lists ARM Android as a host, but its `bare-pack --linked` output uses
platform-level `android: linked:lib…so` resolutions. A separate guard parses the actual
worker header and verifies all 28 Android bindings in both ABI directories; it rejects
architecture-specific resolution branches or disagreement with the addon manifest.

### React Native 0.81 font-size compatibility

Handling `fontScale` in `configChanges` retained state but did not update the rendered
font size. Allowing Android to recreate the Activity fixed glyph size and carousel width,
but another native test exposed stale measurements for unchanged header/navigation text.
Checking a single title was insufficient: its width change happened to bypass the cache.

`native/window/HiraiaFontScale.kt` enables RN's existing
`enableFontScaleChangesUpdatingLayout` fix during application startup, after the standard
entry point registers its flags and before a React context/surface can be created. The
provider delegates every other flag to the same stable/canary/experimental defaults that
the entry point selected. This puts the actual font multiplier in Fabric's measurement
cache keys. The prebuild plugin fails on a different RN minor version, forcing review of
the compatibility shim at upgrade time. Activity recreation still applies system font
metrics; the bounded session cache retains the child's place without writing read events.

### Keyboard focus compatibility

A native Tab sweep caught RN 0.81's clipped-element focus fallback looping through the
current card instead of leaving its nested scroll view. The reader input module uses
Android's standard `FocusFinder` for Tab/Shift-Tab originating in the carousel. Native
`FOCUS_BLOCK_DESCENDANTS` boundaries keep unselected/history/preview cards out of the
keyboard focus sequence; their mouse/touch behavior remains governed by the existing
page rules. This fix is scoped to the reader, not a global change to platform focus flags.

Another native sweep caught the search field's on-screen keyboard remaining open after
Tab moved focus to buttons. In a freeform window it covered the navigation controls;
the accessibility tree still reported their underlying bounds, so coordinate-only checks
missed the obstruction. RN clears its focused-input reference before JS `onBlur`, making
`Keyboard.dismiss()` ineffective there. The search blur callback now asks the native input
module to hide the IME on the UI thread, preserving the newly focused button and leaving
any newly focused text editor alone. Acceptance checks the actual IME state as well as
clicking Next after the Tab sweep.
